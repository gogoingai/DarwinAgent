# Wiki 循环记忆层：小规模验证结果（2026-10-05）

**结论：闭环基本符合设想，有局部经验复用和得分收益；稳定的跨任务收益未通过。暂不建议合并主干。**

完成了固定 10 题的 B0 + R1–R10 正式评分、另外三个对话各 2 题的两轮 Wiki 循环、TravelPlanner 同一题两次独立的一轮 Wiki 循环，以及小规模经验消融和旅行故障回放。没有跑全量题目，没有使用官方 conv-47/49 验证/测试集。所有旧失败运行保留，未改写原实验结果。

## 2. Wiki 是否按设想工作

| 设想 | 实证 | 判断 |
|---|---|---|
| 维护器负责归因与统一写入 | 持久化 events、maintenance 请求/响应、wiki.json；提案器没有独立 Wiki 写口 | 成立 |
| 准入失败、修复、准出采纳/拒绝都留下经验 | 主运行 42 条 entries，58 个 Wiki 版本；包含失败尝试、正式评分、十次决策；拒绝记录未删除 | 成立；条数不作为收益指标 |
| 后续 R 根据经验选方向，同轮重试不重新选方向 | R5 goal 引用 R4 决策归因；每次尝试持久化 base_version/wiki_version/目标，允许相关 S/F/C/P 联合修改 | 成立 |
| 经验有实际作用 | R4 图扩展故障的参数/步数进入归因；R5 依据它收紧扩展并通过对应压力调用，随后采纳 | 有直接证据；不能把分数差全部归给 Wiki |
| 运行与策略经验分开 | 准入错误原已记运行；正式错误原混在策略记录中，本次补了独立 runtime_faults 记录，包含工具错误和候选 C 拒绝事实 | 已补机制与回归；检查拒绝不自动等于代码 bug，原因仍是待验证假设 |
| Wiki 不干扰答题/金标边界 | Wiki 只在优化侧；维护器/提案器读取当前资产、训练问题、生成/候选答案、召回轨迹和原文、评分布尔标志；没有参考答案或判分缺失要素文本 | 成立；回答仍走原有工具/检查/审查链 |
| 经验能够稳定避免重复故障 | 主实验仍有同类准入错误重复，旅行两轮也未自主完成故障链修复 | 未成立，不能保证零故障 |

### 直接收益证据及限制

R4 在题65调用 `f_relation_expand_facts(subject=卡罗琳, relation=涉及人物, scan_limit=100, limit=200)`，遍历 63+288 条边，耗用 30001/30000 步。被拒绝后，R5 的持久化目标引用这次失败，要求收紧种子范围、保持实体截断、恢复主体过滤、补宽参数压力试跑。R5 实际只修改该 F；对应故障调用与更宽的 500/300 参数均通过，正式得分 9/10、无生成故障。失败的 R4 从未替换已采纳基线。

补做两次“只有 B0 当前证据、没有历史失败与归因”的真实提案，使用同一 B0 和短引用协议：两者与 B0 一样，100/200 调用通过，500/300 调用因 search 上限失败；Wiki 链中的 R5 两者均通过，R4 两者均因预算失败。**这支持历史失败经验帮助修复宽参数鲁棒性；不是随机化质量消融，也不能证明答题稳定提升或优于纯向量。**

旅行最终额外做了归因/检查回放：补齐实际候选内容、JSON 类型和冻结契约后，真实维护器从原来的“缺航班”转为定位 C 的冻结容器类型误判；随后 C 修复提案先因未注册 hasattr 被拒绝，又只修数组而漏对象类型，最后在反馈检查事实与通用运行约束后，放行同一份合法历史计划，并仍拒绝非法非数组文本。最后一次反馈包含显式的通用契约修复提示，**这是辅助故障修复诊断，不是纯自主 Wiki 对照，更不是新的正式旅行评分轮次**。新 C 未发布为旅行采纳版本。

## 3. 成本与重复问题

主验证本目录内共 1339 次模型调用：Wiki 维护16、提案16、tools823、answer214、review211、判题59；prompt tokens 15,434,866。这里不包含旧目录冷启动或预检，也不是所有修复尝试的总成本。Wiki 维护仅占调用数约1.2%，没有证据说明它本身是当前主要耗时源。

主验证准入提交15、通过11，冒烟通过11；累计冒烟约762秒，正式阶段约862秒，准入约7秒。实际提案输出16次，其中1次未达到准入提交。Wiki 中 high_degree_in 的 CoverageGap 重复2次，循环内 traverse 的失败重复3次；去重记录并不等于避免重犯。

多对话新目录共447次调用（维护3、提案2），冒烟约778秒，正式阶段约214秒（含恢复的 B0）。缩小正式题量后，冒烟成本占比更大；单纯换维护器模型不会消除工具/答案/审查反复调用的成本。

## 4. 本次已修复的通用问题

- 准入按实际参数绑定识别种子/方向；切片 limit 不再被当作种子；图压力副本保留原数据，空探索不否定已经真实覆盖的方向。运行错误及预算门不放宽。
- 契约不支持的 union type 在模型执行前批量检查；实际参数、步数、边数进入反馈。
- 短资产引用由框架绑定冻结指纹，避免模型反复抄错长指纹；旧接口和身份校验保留。
- LoCoMo 非连续题号按 idx 对齐并检查完整性；通用评价器仅在显式支持 asked 时传子集参数，Travel 不再因签名不兼容崩溃。
- Wiki 维护器收到资产代码、实际工具实现与边界、冻结输入实现、可用 builtins 和单字符串契约类型规则；补失败候选实际内容/JSON类型/检查意见，避免仅凭最终空答案猜测格式问题。
- 故障/失败检查优先保留在压缩轨迹里；正式阶段机械故障另记运行经验，重复记录保持幂等，不新增归因模型调用。
- 修正冷启动提示中“一方面要求 C.stage，另一方面禁止 C.stage”的矛盾。

最终代码框架283项测试：281通过、2跳过；LoCoMo14项通过，Travel11项通过，diff 空白检查通过。离线/记录回放只证明相应接口与状态契约，不冒充真实质量提升。

主十轮及多对话运行期间源码冻结；最后新增的候选内容证据、冻结/契约说明由专项回归和旅行历史轨迹真实归因/提案验证，**未再重新跑一遍最终源码版本的主十轮**。所有旧运行身份、原始轨迹和分数保留。

## 5. 下一步建议（先修这两点，不扩全量）

1. **把动态图任务的准入补齐。** 当前没有 snapshot_root/bootstrap_trial_graph 时，通用 _preflight 直接返回，Travel 的新 F/C 缺少 LoCoMo 那种真实图准入和冒烟门。先对同题真实图增加空返回与输出契约压力输入、合法 JSON 候选、非法候选和冻结容器检查；S/P.extract 未改时复用对应图，改了则构建候选图后检查。不要靠再加 R 轮数才发现这些问题。
2. **把失败检查变成可验证的回归经验。** 现有 _prior_failed_tool_params 已扫描所有正式阶段，包含被拒绝候选的工具实参；不要重复设计一个 F 参数库。补的是 C 失败候选/检查快照和具体失败签名的回放，以及“verified_fix”与具体复现结果的绑定。Wiki 的原因文字仍只是建议，不能覆盖真实检查事实、沙箱契约或用户日期等请求约束。

这两点补完后，仍用单题 Travel 和少量对话验证即可；旅行至少完成一次健康的 B0→提案→准入→正式评分闭环，再讨论合并。不要把本次局部训练分数提升包装成泛化验收。
