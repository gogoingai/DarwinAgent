# Oak 可移植框架重构方案

日期：2026-10-02  
状态：设计方案，尚未实施。问题依据为当前工作区源码及本地验证。  
目标：让 Oak 从两条基准管线共享组件，演进为能够在其他项目中安装、接入领域、构建内核并执行推理的框架。

## 1. 完成后的使用方式

可移植首先指代码、领域能力和内核资产能够离开当前仓库使用，也包括模型服务、工作目录和运行环境可以配置。第一版以 Python 包为载体。

一个新项目只需要提供领域资产、数据适配器、模型配置和工作目录，便能调用同一套引擎完成构建、冻结、导出、装载和推理。接第三个任务时，核心代码的修改量应为零。

验收必须同时满足以下条件：

1. 安装构建产物后，在仓库之外运行，不依赖当前工作目录、`datasets/` 源码或仓库中的 `runs/`。
2. 对话记忆和旅行规划通过同一套构建、推理入口执行，任务差异由领域包及适配器提供。
3. 新领域能注册自己的 schema、函数、检查、提示词及算子扩展，不修改核心角色表和控制流。
4. 导出的内核包含实际运行所需的资产及兼容性声明；移到另一个目录后能装载、验证和执行。
5. Schema、函数权限、证据引用及预算由运行时执行约束；违规不能仅记录告警后继续当作成功。
6. 构建阶段能修订 S/F/C/P；推理阶段使用冻结版本。评测、引擎和适配器不属于自动修补面。

保留现有两阶段与四步循环，以及 S/F/C/P 的工程划分。本文讨论工程实现，不重新认定论文机制或复现成绩；C/P 等扩展的来源标注继续沿用已有文档。

### 2.1 最小复现与验证边界

2026-10-02 的本地检查得到以下结果：

- 一个只声明 `Person(name)` 的 Schema，仍能建出缺主键节点 `Person::`、`Alien` 类型节点、未声明属性和关系。
- 两个主键 `{"a": "x|b=y", "c": "z"}` 与 `{"a": "x", "b": "y|c=z"}` 生成相同节点 ID。
- 证据主体为 Alice、答案文本为 Bob 时，当前主体检查返回空违规列表；证据为空时也返回空列表。这说明该检查没有执行语义上的主体比较。
- 试跑超时设为 0.02 秒、函数睡眠 0.25 秒，实际约 0.256 秒才返回。这里只验证有限任务，未执行无限循环。
- `Config` 只提供主服务 key 时，`LLMClient` 初始化失败；验证没有发送模型请求。
- 现有 16 个 LoCoMo 协议测试通过，本次编写方案时复跑仍全部通过。它们不覆盖上述通用契约。

尚未进行安装包隔离测试、真实跨机器测试、模型服务切换测试或完整基准复评。本文的通过条件是未来验收要求，不是已完成结果。

## 3. 目标架构与职责

### 3.1 三层结构

| 层 | 负责的内容 | 可以依赖 | 扩展方式 |
|---|---|---|---|
| 核心 `oak` | 公共数据契约、Schema 与图验证、内核装载、构建/推理/修补控制流、模型接口、预算和产物管理 | 通用库及公开协议 | 框架版本升级 |
| 领域包 `oak_domains` | 对话记忆、旅行规划的种子资产、抽取策略、领域函数、查询策略、领域检查及词汇 | `oak` 的公开 API | 注入 `DomainSpec` |
| 数据集适配器 `datasets/*` | 原始文件解析、语料切分、官方数据库接线、训练/验证/测试划分、参考答案与评测器 | 核心公共协议和领域包 | 实现 `DatasetAdapter`，绑定冻结评测器 |

依赖方向为：领域包依赖核心；适配器及应用装配两者。核心不导入具体领域或数据集。领域包不读取 benchmark 的 gold、题目类别标签或官方文件布局。

第一版将 `oak` 和 `oak_domains` 作为同一发行包里的独立 Python 命名空间，减少同步升级成本；核心导入不自动导入领域包，领域额外依赖通过 extras 安装。待公开接口稳定后再考虑单独发行领域包。

建议目录如下；这是实施目标，本次不会创建这些代码目录。

```text

  schema/               Schema 解析、引用/类型/公理验证

  operators/            算子规格、执行上下文、受控函数执行

  runtime/              预算、缓存、检查点与运行记录
oak_domains/
  conversation_memory/  中文记忆及可替换的语言/词法策略
  travel_planning/      旅行规划领域资产、派生与计算
```

### 3.2 第一版公共接口

| 接口 | 输入与输出 | 边界 |
|---|---|---|
| `DatasetAdapter` | 将数据转为 `CaseInput`、`CorpusBlock` 和独立 `Reference`；声明 split | 生成侧只取得语料和问题，gold 与标注证据只提供给评测侧 |
| `DomainSpec` | 种子资产、抽取/归并策略、算子与函数规格、查询策略 | 提供领域能力，不控制重试、预算、采纳或回滚 |
| `KernelBundle` | 可装载的 S/F/C/P 与依赖清单，提供 validate/freeze/export/load | 冻结后的运行对象不可修改；所有实际使用资产可追溯 |
| `BuildEngine` | 任务描述、训练输入、验证计划、起始内核、运行配置 → 内核与构建记录 | 控制 B1—B4；阶段调用绑定明确内核版本 |
| `InferenceEngine` | 冻结内核、运行配置、语料/问题 → `AnswerResult` 与证据轨迹 | 无修补入口；工具调用只能经过已发布的 F 与注册算子 |
| `Evaluator` / `Attributor` | 输入答案、参考与允许的语料 → 判决、诊断及状态 | 隔离于生成运行对象；模型、规则、归因及聚合策略一起冻结 |

协议只定义必要语义，避免一次性设计过多后端。第一版继续使用 NetworkX 表示内存图，先稳定公共图契约与序列化版本。

函数统一登记输入类型、输出类型、引用的 schema/算子和实现身份。现有可信手工函数与生成函数可以共存，但都通过同一规格与发布门。不同领域允许配置查询策略及算子扩展；引擎负责执行步骤、超时、证据积累和调用权限。

## 4. 关键改造设计

### 4.1 Schema 与图写入契约

对应 OAK-04、05、06、17。

所有实体和关系候选进入统一校验入口：检查声明类型、字段、dtype、完整主键、空值、端点类型以及 domain/range。系统元数据保留在单独命名空间。继承、union 与多值属性的含义必须先由 Schema 契约明确，再用于校验。

未知类型、非法字段和缺主键默认拒绝，记录候选位置与原因；需要容错导入时，显式启用隔离模式并输出污染报告。关系补节点仅在类型、完整主键及关系签名均合法时允许，节点标记为待补充，不能伪装成完整实体。

节点身份按实体类型与 Schema 指定的完整主键规范序列化。属性规范化按 dtype 执行，字符串是否折叠空白由领域明确，避免在所有领域无条件合并不同标识。不再使用有歧义的字符串拼接。

Schema 是抽取约束的唯一来源：提示词渲染、候选解析及写入校验引用相同版本。协议模板由引擎管理，行为指令由 P 管理；Schema 更新后重新生成对应提示词和约束。

形式验证返回 `PASS / FAIL / UNVERIFIED`，原因包括逻辑矛盾、运行异常、超时或缺少环境依赖。声明必须通过 HermiT 的内核遇到 UNVERIFIED 时不能发布；仅采用静态验证的配置须提前声明，并在 manifest 中记录保障范围。

验收：上述坏候选全部产生明确违规；主键碰撞反例生成不同 ID；同一合法主键稳定去重；新增 Schema 类型能出现在实际抽取约束里；推理器异常不能记作形式验证通过。

### 4.2 内核资产与装载

对应 OAK-03、07、08、18。

manifest 至少包含：包格式版本、内核 ID/版本、兼容的框架版本、资产 kind/id/version/scope、包内相对路径、完整内容摘要、依赖、函数规格、检查实现、提示词模板，以及发布时的校验报告。外部可执行插件记录包及版本/构建身份，不能只登记函数名称。

模型服务与凭据由运行配置提供；内核声明所需能力。收益与评测指纹进入构建记录，不能把某个 benchmark 上的收益当成跨领域收益。导出包不包含 API key、机器绝对路径、数据集 gold 或未请求导出的语料。

scope 分为 universal/domain/dataset；可携带资产不代表可自动提升其 scope。特定数据集经验进入跨领域默认资产前，必须有独立验证记录。

`load()` 检查资源存在性、摘要、引用、兼容性与执行依赖；缺文件即失败。`freeze()` 形成固定执行快照，运行前和运行结束核对身份。Checks 按内核的明确清单绑定，不从可变全局注册表隐式选取。

引擎每次运行记录实际使用的内核摘要。schema、函数调用、检查与提示词都从同一装载对象取得，使 manifest 与执行内容一致。

验收：导出后搬到新目录可运行；篡改文件或遗漏依赖会拒绝装载；修改检查实现会改变内核摘要；执行记录能反查本次使用的全部资产版本。

### 4.3 证据、答案和检查

对应 OAK-08、09、12。

引入 `SourceRef` 与 `EvidenceRef`：携带来源类型、文档/消息标识、定位及内容摘要。正文、图片说明、observation、event_summary、外部数据库和计算派生分别标注。派生标注即使没有消息 ID，也必须有本层可核查定位，不能只填一个非空字符串当作溯源。

答案采用结构化状态：`answered / abstained / execution_error`；评测故障单独属于评测结果。显示给用户的拒答文字由领域及语言配置渲染。可执行的空证据、未知引用、错误引用和计算血缘规则归入核心底线，自动修补不能删除。

主体支持检查分两层：核心校验证据引用和声明结构；领域检查判断声明主体是否由证据及关系支持。跨人物关系、联合主体和多跳推理不能靠简单的名字相等判定。无法确定时返回待复核，不能宣称通过语义验证。

每个检查有适用阶段、严重程度及失败策略：阻断、隔离或复核。固定的框架底线与可修订领域 C 分开；调整领域检查不能关闭框架不变量。生成后语义检查可能需要模型审查，须单独记录方法及不确定性。

归因器可以从切片发现候选问题；判断语料缺失时需要核对完整、已声明的来源范围，返回支持位置或待核实状态。争议题仍计入冻结的原始主指标；人工审计后的另一口径另列，不自动替换原指标。

验收：错误引用、无支持的声明和来源定位缺失可被识别；跨主体但有明确关系支撑的合法答案不会被机械拒绝；执行故障不转换成语义拒答；无法完成支持判断时不会返回确定通过。

### 4.4 修补事务与评价纪律

对应 OAK-10、11、12。

补丁采用结构化表示：目标资产 ID、kind、操作、基础摘要、新定义、诊断理由、失败样本与预期影响。目标只允许内核中可修订的 S/F/C/P。每轮一个显式语义操作；由它引发的确定性重编译作为派生产物登记。

在独立候选目录生成新内核，校验后再运行验证。拒绝时丢弃候选、继续使用原内核；接受时切换发布版本。这样不需要把任意 Python 文件复制回当前仓库，也能处理新增及删除资产。迁移阶段若仍使用文件快照，须记录完整文件集合并正确恢复增删改。

冻结清单覆盖评测器、归因器、参考答案、数据版本、解析/规范化与聚合规则、模型及请求策略。引擎和适配器有独立版本身份，同一轮发生变化即使成绩上涨也不归因到内核补丁。

门控顺序：

1. 资产范围、基础摘要、评测及数据身份一致。
2. 契约检查与函数发布门通过；没有新增硬违规。
3. 评估完成率满足预先声明条件。故障轮标记 INVALID；重跑必须保留原故障与尝试次数，并遵守固定重试上限。
4. 优化集达到预设改进条件，验证集主指标及关键类别不低于预设下限。
5. 系统侧失败归因作为辅助解释；若继续使用“严格下降”作为目标，它必须与第 4 条同时满足。

样本少的类别使用逐题回归清单；容忍幅度、随机性处理及采纳标准在实验开始前固定。验证集反复门控会被逐渐适配，最终泛化结论须来自独立测试集。

已有文档的 conv-26/44/30 分工作为当前实验配置保留。实施前核对现有运行及曝光记录，再判断 conv-30 能否承担独立测试，不能仅因它被命名为 test 就声称尚未使用。

wiki 与 patch-impact 继续追加保留，注明接受/拒绝和资产版本；拒绝的经验不能自动重新注入冻结内核，测试答案也不进入通用经验层。

验收：修改引擎、适配器或归因器不能伪装成合法内核补丁；越界目标被拒；候选新增/删除资产后拒绝不影响基础内核；故障轮不被记为效果退化或成功；评价条件不能随轮次漂移。

### 4.5 模型、预算、缓存和执行上下文

对应 OAK-13、14、15、16，以及上下文隔离风险。

模型路由由应用注入角色到服务配置的映射。未配置 fast 档时继承主服务；显式配置新服务时校验完整参数。第一版支持当前使用的兼容接口，各服务的思考参数、流式能力、超时及代理策略进入服务适配配置，不再由数据集名称决定。

统一 `RunContext` 保存运行 ID、图、内核、模型路由、槽位提取器、预算及产物位置。图和槽位后端具有相同隔离边界，算子不能读取另一个应用的模块全局状态。

预算显式分为 run/round/query scope，与 namespace 名字无关。在并发请求前原子预留，完成后结算；账本持久恢复。逻辑调用、外部请求尝试、缓存命中、token 用量分别计数，哪些受限预先配置，避免缓存调用和付费调用混为一项。

请求缓存按有效服务身份、模型及版本信息、完整实际请求参数、输出协议/客户端语义版本生成摘要。敏感凭据不入缓存身份，隔离需求由非敏感服务别名或租户标识表示。图缓存覆盖完整语料、来源层、S、抽取/审计/归并资产及构图版本；答案与检查点覆盖问题、图、内核和推理配置。

新运行有独立 manifest 和目录，但相同依赖允许复用可验证缓存。检查点只在全部依赖匹配时续跑；原子写入采用唯一临时文件，避免多个进程写同一个固定 `.tmp`。

函数试跑在可终止的进程中加载源码及规格，绑定只读图/输入，超时终止并记录。AST 检查保留为前置约束；进程隔离用于可靠超时和资源控制，不能据此宣称支持任意不可信 Python 的完整安全隔离。第一版只发布受控函数实现。

验收：单服务配置能初始化；切换服务或策略不误命中缓存；只改后续会话内容也会更新图身份；重启后预算继续有效；两个应用并发不串图/槽位后端；超时工作进程结束后引擎可继续处理后续任务。

## 7. 验收矩阵

第三领域建议采用小型合成的设备维护知识库，包含设备、故障、维修记录、零件与技师。覆盖联合主键、关系查询、时间过滤、聚合、不可回答和跨主体证据，避免第三个例子仍然沿用对话字段。

| 验收项 | 方法 | 通过标准 |
|---|---|---|
| Schema 边界 | 注入未知类型、关系、字段、坏 dtype、缺主键及非法端点 | 每个反例明确拒绝或隔离；不进入发布图 |
| 节点身份 | 分隔符、Unicode、联合主键、声明类型规范化样例 | 不同合法键不碰撞，同一键稳定去重 |
| 检查执行 | 删除必需检查、破坏证据、篡改内核文件 | 未通过的执行不能当作有效答案发布 |
| 修改传导 | 修改 S、P、归并规则、后续语料、来源层 | 相关阶段失效并重建，未受影响阶段可复用 |
| 函数执行 | 超时任务、非法调用、错输入输出类型 | 及时结束、返回结构化错误、后续任务继续 |
| 上下文隔离 | 两领域并发，配置不同图及槽位提取器 | 各自取得对应数据与后端，无串用 |
| 预算恢复 | 多个并发请求竞争最后额度，重启后续跑 | 不因名字或重启绕过限额，不超发请求 |
| 修补事务 | 越界目标、基础摘要不匹配、资产增删、冻结依赖变化 | 正确拒绝；基础内核完整，审计保留 |
| 评测纪律 | 故障轮、争议题、指标下降、未完成评估 | 原指标完整披露，争议不自动扣出，非法轮不采纳 |
| 两任务兼容 | 合法 fixtures 差分、录制响应回放、约定规模真实复评 | 等价迁移不改变合法行为；正确性修复造成的差异单独列明 |
| 安装包独立 | 在空项目安装 wheel，清除源码路径影响后运行 | 运行从安装包加载，不依赖源仓库或源码编辑安装 |
| 第三领域 | 外部项目新增 DomainSpec 与 Adapter | 核心无修改，构建/冻结/导出/装载/推理完整通过 |
| 跨环境 | 目标 Python/OS 组合测试，形式推理依赖单独声明 | 仅将实际通过的组合列入兼容性说明 |

离线测试使用确定性测试模型后端或录制响应，验证接口、契约和流程；真实模型评测用于验证效果，两者分别报告。没有完成跨机器验证前，只能报告仓库外安装和资产迁移已验证。

## 8. 兼容与范围控制

旧入口先保留，通过兼容层委托新引擎。旧的图、缓存和运行记录保持可读，新增产物使用独立格式及目录；ID 与图格式升级后整体重建或显式转换，不原地覆盖历史结果。

第一版先稳定 Python 公共 API、两领域与一个外部示例。CLI 可以作为这些入口的薄封装。分布式任务调度、多种图数据库、自动发布和跨语言 SDK 在接口验证后再评估。

本方案先独立成文；现有文档和代码尚未同步修改。实施时每一阶段完成后再更新对应说明，避免把目标设计写成已经实现的能力。
