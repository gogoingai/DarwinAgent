# 动态构图与资产修改信号

LoCoMo 的新 g1 运行默认使用 LLM 按当前 S 构图，启用 Wiki，并开放 S/F/C/P 修改。原子事实、事实编号和向量索引保持不变；其余实体、属性与关系从当前事实和来源原文中生成，不再受人物／主题／会话三类预设映射限制。

S 负责声明图的类型、字段与关系，P.extract 指导模型构图。每个生成节点和每条边都必须引用当前批次的事实编号、该事实对应的来源 ID，以及来源中的逐字证据。固定程序校验类型、主键、关系端点、来源和实例约束。模型不能改写原子事实，也不能生成没有证据支持的端点。

构图结果以事实、原文、S、P.extract、执行配置、模型连接身份和构图实现为键持久化。修改 S 或 P.extract 会生成新的图；只改 F、C 或其他 P 时复用相同的图。准入、试跑、正式作答和持出评测使用同一个构图器。收到响应和完成构图分别落盘；已提交但没有回执的请求保持 unknown，重启不会自动重发。

## 如何定位需要修改的资产

每轮训练反馈包含实际执行阶段、图结构摘要和资产修改线索。图摘要记录节点与关系数量、未物化的声明、没有关系的事实及图摘要指纹。图信息优先占用一部分反馈预算，避免长答题轨迹把它挤掉。

| 资产 | 可观察线索 | 提案前需要核对 |
| --- | --- | --- |
| S | 所需结构未声明、声明结构未物化、构图类型校验失败 | 原始事实是否支持该结构，当前 S 能否表达它 |
| F | 参数或执行错误、空结果、检索遗漏、截断、遍历缺失 | 信息是否存在于图中，工具是否正确取出 |
| C | 检查拒绝、输入类型与规则不一致 | 检查是正确拦截，还是有证据证明规则误拦 |
| P | 构图遗漏、检索决策、作答或审查偏差 | 信息首次在哪个阶段丢失或被误用 |

这些信号是候选原因，不能仅凭答错或图中没有某类节点就下结论。Wiki 保留图、事实与训练轨迹原件，记录各版本图的差异。提案器可以按训练题、对话或阶段查询原件与历史反例，再在补丁理由中说明观察、候选原因和预期可测变化。验证集、测试集的逐题反馈不会进入这一训练归因链。

查询优先使用 `scope.evidence_refs` 按反馈中的完整证据 ID 读取 `raw` 原件，关联修订说明会一并返回；也可叠加训练题或阶段过滤。`raw` 和 `summary` 不调用维护模型。`regroup` 会分段调用模型再合并，仅用于已缩小范围的多份证据比较；`max_chars` 只限制返回长度。

## 运行入口

```bash
python -m datasets.locomo.run --arm g1 --train-only \
  --dataset-repo justis-xu/memory-eval-zh --dataset-revision main \
  --cases conv-26 --train-question-ids 0,1 \
  --rounds 1 --output runs/new-llm-graph
```

题号须存在于对应对话。命令指定 HF 数据源，首次加载后在输出目录锁定实际提交和文件校验值；继续运行复用该提交。新运行从原始对话准备固定事实，保存到 output/memory，再按 S 动态构图。仅提供对话模型时声明无向量模式；需要复用已有事实和向量时显式传入 --memory-root。模型连接由操作者提供。

`--scope` 默认 `sfcp`；可显式选择 `p` 或 `pf` 限制修改范围。`--optimization-mode` 在 g1 下默认 `wiki`。`--graph-mode llm` 是默认构图模式，`--graph-rebuild` 是其兼容别名。`--graph-mode frozen` 和 `--graph-mode projection` 用于显式复现旧的冻结图或固定投影路径；这些模式及 v0 均须显式传入 --memory-root。旧运行不会被自动迁移或改写，新路径应使用新输出目录。

离线记录式测试验证数据流、缓存、来源与失败边界；真实模型能否正确构图、定位原因并提升得分，需要单独进行受控验收。

## 单题故障恢复

候选修订次数耗尽会记录为 `FeedbackExhausted`，保留候选、检查和审查意见。审查器能看到此前的修订历史，但不能把审查意见当事实证据。审查耗尽的题在同一阶段身份下只获得一次立即恢复机会，使用新响应并携带失败反馈；外部服务故障仍按退避策略重试。成功题、事实和图直接复用，失败检查点原始字节先归档再替换，重启不会重置自动恢复预算。

恢复仍失败时保留执行故障，不能伪装成语义拒答。Wiki 和提案器收到 `fault_category`，审查耗尽会提示查询同题来源及历次候选，检查 P.review 与 P.answer。

报告用 `execution_status` 表示轮次执行状态，`adopted_measurement_status` 表示已采用版本的测量状态，`unhealthy_stages` 保留仍未完整测量的历史阶段；存在未解决的阶段故障时，总 `status` 仍如实标记失败。已恢复的单题故障另计入稳定性统计。采纳仍遵循原得分门槛，同时披露 `comparison_status`：基线不完整时，后续版本完成作答不能单独证明质量提升。
